## Mandatory complete Knowledge Base discovery and reading

Before a new development workstream, major implementation phase, architectural change, requirements reconciliation, or substantial Knowledge Base baseline change, recursively discover **every file under `knowledge/`, including every subdirectory**, and complete the following review before application edits. The four canonical documents are entry points, not the entire Knowledge Base.

Read complete readable contents, not filenames, excerpts or summaries: Markdown and Mermaid source; JSON records and their relationships; PDF and DOCX text, tables and relevant embedded diagrams; PNG diagrams, screenshots and illustrations; and technical TXT, Python and CSS assets. Use appropriate extraction and visual inspection tools. Explicitly account for unreadable, unsupported, missing and inconsistent files; an inventory or successful text extraction alone is not proof of visual review. Report limitations and resolve coverage gaps before claiming complete coverage or proceeding with affected implementation.

Discover all available documentation families: System Context, Use Case, Activity, Sequence, Component Architecture and Entity Relationship diagrams; architecture decisions; requirements registries; acceptance criteria and MVP roadmaps; test plans; Feature Catalogue and User Guide; execution status, evidence and audit records; security/authorization specifications; IoT/device architecture; and payment/booking specifications. Consult the relevant complete workflow diagrams, including `knowledge/01_ActivityDiagram_Customer_Booking_and_Online_Payment.md` for that workflow.

Record actual coverage in existing authorized execution/progress records or the task report; do not create another knowledge document without owner approval. A reusable full-reading ledger must identify the baseline, each file path and SHA-256, review method, actual reading/visual coverage and unresolved limitations. Never label hashing, enumeration or parsing as a completed human/agent content review. Never claim all files reviewed unless every discovered file is accounted for and required readable/visual review is complete.

### Verified reuse for subsequent tasks

A subsequent task may reuse an earlier **verified full-reading ledger only** if all files are accounted for, hashes exist, reused files remain byte-identical, every changed/new file is fully reviewed, relevant canonical documents and task-specific sources are freshly consulted, and no reading-coverage gap remains unresolved. Re-inventory recursively and compare hashes before reuse. If any condition fails, repeat the required full review. Distinguish fresh rereading from verified prior coverage; a historical audit count or manifest checksum alone is not a full-reading ledger. This rule avoids unnecessary repeat reviews without permitting incomplete discovery.

### Authority, traceability and architecture

Canonical owners, explicitly approved decisions and authoritative registries govern implementation. Supporting diagrams, original proposals, mockups and historical documents supply context, not approval. For conflicts identify both sources, their actual authority/approval, and the unresolved question; preserve approved architecture and canonical requirements, record unresolved conflicts and never invent owner approval. Newer timestamps do not establish higher authority.

Before application edits trace the bounded change to requirement IDs, MVP acceptance criteria, approved architecture decisions, owning backend module/public ports, frontend components, database entities/ownership, security restrictions, relevant activity/sequence diagrams, existing implementation/tests and known blockers. Verify the current approved stack against canonical records: Java 25, Spring Boot/Spring Modulith, Modular Monolith, Hexagonal Architecture, Next.js/React/TypeScript, PostgreSQL/Flyway, module-owned persistence and scoped RBAC/ABAC. No microservices, Redis, Kafka, alternative framework, authentication mechanism or provider without required architecture approval.
